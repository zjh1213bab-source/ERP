# 预下单款式来源（简易版）

每款可选“上传图片新款”或“已完成打版商品”，同一预下单可混合多款。

图片新款支持效果图和最多12张细节图，有图片时款式名称可空；既没有图片也没有名称则拒绝空白款式。新款款号由版房填写，业务端只读。保存后自动建立关联开发单与六阶段打版流程，客户图片同步到开发资料。未填款号不能完成新款的制版阶段。

已打版商品来自样衣库已锁定、打版完整完成且当前可用的版本，变更中或旧版不能选。名称、款号和效果图由后端带入，不接受客户端冒充。预下单保存样衣来源快照，正式转单时复制独立技术资料、已完成打版证明和样衣快照，保留原样衣与原订单，后续仍需原有技术确认及本订单封样确认。

版房在“打版流程 → 制版 → 款号”填写，保存后同事务回写关联预下单，并记录前后值、操作人和时间；已转单但尚处草稿/技术阶段时也同步对应订单款式。已完成制版要退回重做后才能改款号，已锁定复用商品不能直接改款号。

## 完整版：接口和数据

GET /api/pre-orders/available-products 返回当前权限范围内的可用样衣商品摘要。预下单明细新增 source_type（new/archive/legacy）、sample_archive_id、source_snapshot；tech_packs 新增 source_archive_id。schema.js 与 db.js 同步补列，仍为372表、445索引；父子引用已登记 audit-demo-data.js，旧数据保留 legacy，不追溯伪造开发记录。

新款源保存和开发创建在预下单同一事务内执行；按 pre_order_item_id 幂等关联，面辅料新品审核复用该开发单，避免一款两套开发流程。存在未完成或未准入审核的面辅料请求时，不能跳过面辅料确认直接进入打版。

预下单版本继续以 revision/version 乐观锁防覆盖。版房款号使用 tech_packs.updated_at 作并发令牌，冲突409；回传款号、更新来源版本、操作事件与阶段内容同事务，失败全部回滚。正式转单的样衣复制也在订单事务内执行，来源版本失效时拒绝转单并回滚，原样衣不能被重新分配给其他订单。

业务更改源样衣和版房改号均有来源校验。仅查看预下单即可读取商品摘要，不额外暴露整套技术快照；跨主体样衣仍按后端 companyScope 判定。业务账号不能借预下单接口填写新款款号。打版已完成或资料已锁定后，仍按既有变更流程处理。

验证：test-preorder-sources.js 43项接口/业务断言，test-preorder-sources-ui.js 10项浏览器验证（真实图片上传、空名称、商品选择、版房改号回传），test-confirmation-lifecycle.js 123项回归；另跑RBAC、深浅色页面巡检、旧库迁移副本与空库结构对比。全量冒烟仍在既有采购夹具 smoke-test.js:1286 退出，不计全过。

部署：frontend 下 npm run build，deploy/win/reload-lan-preview.ps1 在线备份后重启迁移，再核对 health.code_stamp 和数据体检。没有新增环境变量、微信参数或密钥。回滚应恢复配套代码及备份，不要只清来源字段，避免历史关联断开。
