# 把项目交给另一个 AI（ChatGPT / Codex / 其他）

> 本文是**给人看**的交接手册。给 AI 读的入口在仓库根目录 `AGENTS.md`。
> 目标：换一个模型继续干，不出现「说改好了其实没生效」「把已经踩过的坑再踩一遍」。

---

## 一、先认清这个项目的交接难点

| 难点 | 具体表现 | 对策 |
|---|---|---|
| 代码太大 | 后端 8.5 万行 + 前端 7.4 万行，任何模型上下文都装不下 | 只给**入口 + 地图**，按模块现查现改（`AGENTS.md` 第 1 节） |
| 隐性约定多 | 40 多条「违反会静默出错」的规则（事务、孤儿、权限、时区…） | 全部写进 `AGENTS.md`，并要求 AI 先读 |
| 验证不在 CI 里 | 没有 CI，全靠本机跑冒烟 / RBAC / 巡检 | 交接时必须让 AI **报出冒烟数字**，对不上就是没接住 |
| 服务是常驻进程 | 改完不重启，health 照样 200，看起来"生效了" | 只认 `code_stamp` 与文件 mtime 一致 |
| 仓库没有远端 | 105 个提交全在本地磁盘，云端 AI 拿不到 | 要么推私有仓库，要么走「本地 CLI」或「打包上传」 |

**一句话判断接住没有**：让 AI 独立做一个小改动，然后报出 `smoke` 通过项数与 `code_stamp`。
它报不出来、或数字不对（不是 2309）——就是没接住。

---

## 二、三条路径，按能力从强到弱

### 路径 A：推到私有 Git 仓库 + ChatGPT Codex（推荐，如果允许上云）

适合：能接受代码放到 GitHub 私有仓库（含业务逻辑，不含真实客户数据——`.db` 已在 `.gitignore`）。

1. 建私有仓库，把 `erp-mindmap/` 推上去（**确认 `data/*.db`、`.env` 没被提交**）。
2. 在 ChatGPT 里连 Codex / 授权该仓库。
3. 第一条指令固定为：
   > 先读仓库根的 `AGENTS.md`，然后只做一件事：跑通环境并报出 `smoke` 的通过项数与 `code_stamp`，
   > 不要改任何代码。
4. 它报出 **2309 / 0** 才算接住，再分配任务。

优点：AI 能自己读代码、跑命令、看结果，闭环最完整。
风险：真实业务数据别上云；先把 `.db`、`uploads/`、`.env` 从仓库排除。

### 路径 B：本地跑一个能读文件的 AI（Codex CLI / 有本地权限的 Agent）

适合：数据不方便上云。

1. 在项目目录启动 CLI（如 `codex`），把 `AGENTS.md` 作为项目说明。
2. 同样先让它 **只做自检**：`npm run smoke` + `curl /api/health`，报数字。
3. 之后每个任务都要求它：改 → 重启（`reload-erp.cmd`）→ 跑三件套 → 报数字。

优点：数据不出机器、能跑真实验证。缺点：要在这台机器上装、消耗本机资源。

### 路径 C：网页版 ChatGPT 对话（只能上传，不能执行）

适合：只让它做**方案设计、代码审查、写单个文件的补丁**，不适合让它改这个仓库。

限制（必须接受）：它看不到运行结果，改完得你本地应用 + 你本地验证。
所以**每次只喂一个模块**，不要奢望它"接手整个项目"。

1. 生成交接包（见第三节），先上传 `00-AGENTS.md` + `03-code-map.md`。
2. 第一条指令：
   > 你是这个 ERP 项目的接手人。先读 AGENTS.md 与 code-map，然后告诉我：
   > 订单从下单到结案的完整链路要经过哪些表和哪些接口？答完等我确认再动代码。
   （让它复述链路，是检验它真读了、还是编的）
3. 之后按模块下任务，每次只贴**相关的那几个文件**，要求它输出**完整文件内容或 unified diff**，
   不要"片段省略号"。
4. 你本地应用补丁 → `reload-erp.cmd` → 跑三件套 → 把失败项贴回去。

**判断它是不是在编**：只要它给的接口路径/函数名在 `03-code-map.md` 里查不到，就是编的。

## 三、生成交接包

```bash
cd erp-mindmap/backend
node scripts/make-handoff-pack.js            # 生成到 ../handoff/
node scripts/make-handoff-pack.js --zip      # 再打成一个 zip（ASCII 文件名，跨平台不乱码）
```

产出（都在 `handoff/`）：

| 文件 | 内容 | 用途 |
|---|---|---|
| `00-AGENTS.md` | 给 AI 的项目入口（约定 / 雷区 / 验证） | 每次对话第一条就喂它 |
| `01-code-map.md` | 自动生成的**模块 → 文件 → 接口**地图 | AI 查「这个功能在哪」而不是瞎翻 |
| `02-status.md` | 现状：版本、表数、冒烟数字、已完成模块 | 让它知道什么已经做完 |
| `03-recent-changes.md` | 最近三个版本的改动与验证 | 让它知道最近的坑 |
| `04-schema-summary.md` | 369 张表的表名 + 关键列 | 改数据前先看 |
| `05-verify.md` | 怎么跑验证、怎么判断真生效 | 防止「假绿」 |

单个模块的任务还可以追加导出该模块源码：

```bash
node scripts/make-handoff-pack.js --module orders    # 额外导出订单相关路由/服务/页面
```

## 四、交接后的第一周怎么安排

1. **第一天**：只让它自检 + 复述链路，不改代码。它答不出「订单有哪 8 个状态、每步门槛是什么」就退回重读。
2. **第二天**：给它一个**只改一处**的小任务（例如某个报表加一列），看它是否：跑冒烟 → 报数字 → 提到重启。
3. **第三天起**：按模块派活。每个任务都要求「改完报三件套数字」。
4. **永久要求**：任何"已完成"的结论，必须附 `smoke` 通过数、`rbac` 问题数、`code_stamp` 时间。

---

## 五、最容易出事的五个地方（提前告知接手人）

1. **在 3000 端口或正式库上跑冒烟** → 会写脏生产数据。必须复制库 + 换端口。
2. **改完不重启就验证** → 读到的是旧代码，得出"我的改动没生效/生效了"的错误结论。
3. **事务里 `return fail()`** → 不回滚，半截数据落库。
4. **删父行不删子行** → 零外键，留孤儿不报错，几个月后报表对不上。
5. **按名字找工序节点** → 业务改名就静默失效。一律按 `code`（`inspect` / `pack` / `cut` / `sew`）。

---

## 六、不建议做的事

- 不要让新的 AI「重写一遍」。这套系统的价值在 40 多条血泪约定和 2309 条断言里，重写等于清零。
- 不要同时让两个 AI 在同一份工作区改代码（会互相覆盖，且都没跑验证）。
- 不要把 `.db` 或客户真实数据传到任何云端对话里。
- 不要因为"新模型说这个设计不好"就重构核心链路（订单状态机、库存三轨、权限来源）。
  要改先让它说清楚：改完这 2309 条断言里哪些会变、为什么。
