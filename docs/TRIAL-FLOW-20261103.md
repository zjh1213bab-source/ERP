## 完整版

### 覆盖的业务链路

真实登录 → 预下单 → 图片新款开发 / 已打版样衣复用 → 面料寻样与驳回重找 → 业务确认 → 打版准入审核 → 制版填款号 → 工序、样衣、业务、工价核价阶段 → 样衣冻结归档 → 预下单转正式订单 → 逐款技术确认及样衣双确认 → 接单评审 → 成本审批 → 外协分单 → 生产 → 首件检查与放行 → 逐款色报工 → 尾期验货 → 成品入库 → 出库 → 自动应收 → 模拟收款核销 → 结案。

本次“全流程”指上述销售订单主链。**不等于**已覆盖 ERP 的所有模块；没有模拟原料采购收货/领退料、外协供应商结算、月度工资发放、实际运输签收或微信支付。
现有客户/物料/供应商/工厂主档未为跑通流程而改价、改规格或增加信用额度。
业务动作全部通过接口及状态机执行，没有用 SQL 直接把实测业务状态改为完成。

### 本次发现与修复

| 问题 | 原行为与实际影响 | 修复后的行为 |

| 账号与员工脱节 | 同手机号账号存在但未绑定朱佳豪员工档案，自助归属和报工身份可能不一致 | 管理员可显式关联同手机号在职员工；校验公司、重复绑定与并发，不改密、不增权，更新身份后撤销旧登录 |

| 不完整样衣提前锁定 | 打版六阶段可完成，但辅料/工艺说明仍为空；归档锁定后开发确认又拒绝，形成死路 | 归档与开发确认共用 `confirmBlocks()`；资料不齐不归档。已出现的实测旧版通过样衣变更与修改复核补正，旧版保留 |
| 归档后编辑存在旁路 | 开发单状态仍是 draft 时，基础编辑/明细编辑可能越过已完成打版锁 | 两类编辑接口均检查样衣流程完成锁；明细编辑也检查待审业务变更 |
| 多款只查一张开发单 | 查询“最新一份已确认开发单”，可能一款确认放过另一款 | 按明确款式关联、预下单来源、唯一款号/名称解析逐款归属；缺任何一款或该款新版未确认即拒绝 |
| 多款首件互相覆盖 | 首件引用全单最后一份开发资料，一款首件可能放行全单；另一款技术版还会错误地让本款首件失效 | 首件登记与页面增加款式选择；每款绑定自己的当前冻结版，按全部款式检查门禁；改版只使相应款式首件失效。已有结案订单的首件历史仍可查 |
| 结案只看第一张应收 | 没有应收或第一张已收清时，可能漏掉应收生成失败/其他未收款 | 检查有效应收金额覆盖订单金额，并检查全部有效应收未收额；原有人工强制结案路径未放宽 |
| 状态写入缺少并发保护 | 校验后其他进程修改订单，旧操作可能继续覆盖 | 状态写入比对原状态与 updated_at；冲突返回 409 并回滚日志写入 |
| 出入库/自动应收丢说明 | 入参 remark 被忽略，库存流水只有“成品入库/发货出库” | 出入库备注验证后随流水和日志保存，默认沿用订单说明；自动应收保存订单说明快照，保留实测性质 |

### 仍存在的不足与边界

1. **计件工资未闭环**：现场 `piece_rates` 为 0 条，44 条报工快照中的基础工价为空。系统保留空值，没有把缺价当作 0 或猜工价，也未生成真实员工工资单。
   打版“核价”完成并不等于生产扫码已有可结算单价。下一步应明确每款实际生产工序与计件工价映射，并对缺价给出统一清单；不能简单把一个“车缝”总工价摊给各员工。
2. **默认生产模板偏通用**：本次生成 13 个默认节点，11 个通过报工完成，入库/出库节点由单据反推。样衣实际选用工序和通用节点仍需明确映射，不能认为默认出现的印花/洗水等节点一定适用于每款。
3. **管理员实测不能代替岗位验收**：朱佳豪账号原本是管理员，可代办多个审批角色。本次另外运行岗位 HTTP 测试和权限审计，但没有冒用其他真实员工逐岗审批。
4. **全量冒烟尚未通过**：单公司和多主体两种隔离环境均运行到 179 项通过、8 项失败，然后在 `smoke-test.js:1286` 因空采购夹具取 `.id` 中断。失败还包含依赖缺失成本对象/供应商夹具的断言，不能仅凭本次主链通过就宣称整个系统可交付。
5. **保留数据需要管理**：按用户要求没有清理这些实测单据、模拟收款和报工。不要把这批记录当普通烟测残留执行自动清理；复核时按 `SCBH-20261103-` 或上述完整标记查找。
