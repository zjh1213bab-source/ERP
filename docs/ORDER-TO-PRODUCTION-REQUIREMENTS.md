# 订单到车间生产：现状审查与开发需求

> 审查日期：2026-10-28  
> 范围：客户/销售下单 → 技术与成本评审 → 分单 → 车间任务 → 工序报工 → 成品入库。  
> 本文是基于当前源码的静态审查，不代表已执行运行验收。

## 一、结论

**下单入口存在，正常订单也有通往生产的状态链；但“订单到车间生产”目前不能认定为数据闭环。**

销售可以在「销售订单 → 新建订单」录入订单，并按款、颜色、尺码、数量和美元单价保存。订单可以经过接单评审、技术确认、成本审批、分单，进入生产后自动生成 13 个工序节点；车间可以在订单详情中报工。[Orders.vue](../frontend/src/views/Orders.vue) · [orders.js](../backend/src/routes/orders.js) · [orderFlow.js](../backend/src/services/orderFlow.js)

审查时发现可绕过业务门槛的路径：财务审核后可以不创建分单记录就把订单改成「已分单」；生产或仓库角色可以从「已分单」直接将整张订单入库；报工接口还存在缺少工序信息时跳过首件门禁的分支。报价单和客户商城转单则会用「待定/均码」占位，缺少后续补全订单尺码明细的编辑入口。这些问题会造成“系统显示已入库/已生产”，但数据没有证明它经过实际车间生产。

本轮已在代码中补上首批服务端门禁和草稿明细补录入口，详见“2.3 本轮已落地的修复”。这代表关键绕行路径已有保护，**不代表完整生产闭环已验收**：目前仍按整单入库，分单/工序报工没有按颜色尺码和工厂任务分配，且尚未运行端到端验收。

因此，README 和旧差距分析中“产前链路已全部闭环”的描述只能表示模块和流程已有实现，不能作为订单到车间的上线验收结论。下文 P0 项关闭前，不应以此链路承载正式生产数据。

## 二、当前业务入口与实际流转

### 2.1 下单入口

| 入口 | 当前行为 | 审查结论 |
|---|---|---|
| 员工手工下单 | 「销售订单」页有「新建订单」；`POST /api/orders` 创建草稿并保存各颜色、尺码数量及单价。 | **入口可用**，是目前最完整的生产数据入口。草稿现可补改颜色尺码和金额；客户、交期等订单头字段仍可留空。 |
| 报价转订单 | `POST /api/quotations/:id/convert` 生成草稿订单，报价阶段没有颜色尺码时写入「待定/均码」。 | 现在只允许已接受报价转单；销售可在草稿补齐明细，未补齐前技术确认会被拦截。来源单号/报价版本仍未结构化关联到订单变更记录。 |
| 客户商城询价转单 | 客户选择商品和总数量后提交询价，颜色、尺码、交期等仍主要写在备注中；转单生成「待定/均码」草稿。 | 现在只允许已确认询价转单；销售可在草稿补齐明细，未补齐前不能进入技术确认。商城仍是询价入口，不是结构化颜色尺码的客户正式下单入口。 |

### 2.2 订单到车间的代码路径

预期状态链为：

```text
销售建单(draft)
  → 接单评审通过 + 技术资料确认 + 定制单打版完成(tech)
  → 成本审批通过(finance)
  → 分单到本厂/外协(assigned)
  → 生产中：初始化工序并由车间报工(production)
  → 按实际合格产出入库(instock)
  → 发货(shipped) → 结案(closed)
```

源码中的 `orderFlow` 对进入技术确认要求接单评审通过、存在已确认开发单；定制单还要完成打版流程，并检查适用的客户封样确认。进入「已分单」要求成本单已审批；进入「生产中」会初始化默认 13 道订单工序。分单接口首次提交时也会将订单推进到「已分单」。

但以下实现差异破坏了链路的事实一致性：

1. 审查时 `/api/orders/:id/transition` 可直接把成本审批通过的订单推进到 `assigned`，没有检查是否已有有效分单记录。本轮状态机已要求成本审批通过且分单累计量覆盖订单总量；进入 `production` 前也再次校验整单分配。
2. 审查时 `/api/dispatch` 没有校验各次分单的累计数量。本轮已限制累计分单不得超过订单量，并禁止订单进入生产后删除分单；分配仍未按款/颜色/尺码落到独立生产任务。
3. `dispatch_orders` 仍仅关联订单、工厂和总数量；订单工序、报工记录没有关联到分单或工厂。多厂拆单后只能看订单级汇总，无法证明哪家车间完成了哪一部分。
4. 本轮 `/api/reports` 已要求 `node_id`、校验节点归属和订单生产状态，并限制每道工序累计报工不超过订单量；首件门禁仍应用于非前置工序。报工暂未关联独立生产任务/工厂，也没有相邻工序数量守恒和数量变更审批。
5. 订单工序仍可通过 PATCH 人工改成「已完成」。报工达到整单数量时，本轮会自动完成节点；入库前还要求检验节点已完成、合格报工覆盖整单并有已放行尾期验货记录。
6. 本轮已禁止 `assigned` 直接入库，只能从 `production` 入库；通用状态接口和批量流转不能伪造入库/发货，必须走对应库存接口并生成库存流水。入库依旧按整单订单尺码计划一次性处理，没有部分完工/部分入库的数量结转。
7. 默认工序是所有订单通用的 13 道工序，包含水洗、印花、绣花等可能不适用的工序；订单流程尚未体现款式工艺路线版本与车间派工路线的绑定。

### 2.3 本轮已落地的修复（首轮，不等于全部 P0 完成）

- 销售订单详情增加草稿明细编辑；报价转单仅接受已接受报价，商城询价仅允许已确认后转单；转单产生的「待定/均码」可在草稿阶段补齐，未补齐时不能通过技术确认。
- 分单累计量不得超过订单总量；直接推进「已分单」和「生产中」必须确认全量已分配；进入生产后不能删除分单记录。
- 报工必须引用所属订单的工序节点，只能在生产中报工；数量/工时必须有效，同一工序累计报工不超过订单量，报满后自动完成该工序。
- 入库要求订单处于生产中、检验节点已完成、检验工序合格报工覆盖订单量，且存在已完成并放行的尾期验货；通用单张/批量状态迁移不能替代真实入库或发货。
- 入库和发货完成后同步客户状态通知；发货后补执行开应收和成本归集副作用。
- 未完成：按明细/工厂创建生产任务、任务级报工和数量守恒、部分入库/部分发货、报工修改审批、工艺路线配置，以及真实数据的端到端验收。

## 三、开发需求与优先级

### P0：形成可信的订单生产闭环

#### R1. 建立唯一的订单状态迁移入口

- 所有 `orders.status` 写入必须经过同一状态机服务；分单、入库、发货等路由不得自行绕过校验修改订单状态。
- `finance → assigned` 必须有已审批成本和有效的工厂分配；若允许先部分分单，状态/数量必须明确表达“部分分配”，不能显示为完整已分单。
- `assigned → production` 必须对应可追溯的生产任务。无分单、无生产任务或分配数量为零时拒绝迁移，并向前端返回可执行的缺项清单。
- 入库只能从生产态或生产任务的实际完工批次发生；不得从 `assigned` 直接将订单改成已入库。
- 验收：直接调用状态接口跳过分单、直接从已分单入库、重复迁移、越级迁移均被拒绝且不产生库存/状态副作用；失败原因与订单号写入操作记录。

#### R2. 让分单数量和车间任务按订单明细闭合

- 分单须能分配到工厂/车间、订单明细及颜色尺码；保存分单时计算“订单量、已分量、剩余量”。
- 同一明细所有有效分单的累计数量不得超过订单量；删除/撤销分单必须同步释放已分配量并留痕。
- 每个本厂分单生成有唯一编号的生产任务，关联订单、分单、工厂/车间、款式工艺版本、颜色尺码数量、计划交期和责任人。外协分单也保留独立交接与验收数量，不混入本厂工序报工。
- 验收：一订单拆两个工厂、同一尺码分批分配时，各任务数量可分别查询；超分配被拒；订单、任务、工厂维度的计划数和剩余数相互勾稽。

#### R3. 补齐草稿订单和转单后的结构化明细

- 草稿订单必须可编辑订单头与订单明细，至少支持修正客户、客户 PO、交期、款号、颜色、尺码、数量和币种/价格快照；提交技术评审后冻结，修改需走变更版本并记录影响范围。
- 手工下单在提交评审前校验客户、款号/款名、交期、有效数量及每个尺码的颜色/尺码编码。允许暂缺的字段应明确标注为待补，不得静默按空值进入后续流程。
- 报价转单必须要求报价状态为「已接受」；客户商城转单必须要求询价状态为「已确认」。重复提交必须幂等，保留源报价/询价 ID。
- 报价和商城订单必须提供结构化颜色/尺码数量；若询价阶段不采集这些信息，转入 ERP 后必须停留在可编辑草稿，并在补齐前禁止技术评审/生产排程。禁止以「待定/均码」作为可生产数量进入车间。
- 验收：客户确认前无法生成可流转订单；确认后订单明细可追溯回报价/询价；缺颜色或尺码时不能通过提交评审；转单后能补齐并冻结明细。

#### R4. 将首件/工序门禁落实到服务端报工接口

- 生产报工必须引用有效生产任务、工序节点和该节点所属订单/分单；不接受只有 `order_id` 的无工序报工。
- 服务端校验 `node_id` 与任务、订单、工厂归属一致；车缝及之后工序必须有当前款式版本下有效首件放行，并检查放行量上限。
- 报工数量、工时必须为有效正数；同工序累计合格数与不良数不得超过该任务的可报数量。工序间数量差异必须作为损耗/返工/补数原因记录。
- 工序状态由报工和复核记录推动；若保留人工更正，必须说明原因、保留修改前后值和审批人。
- 验收：无首件、过期版本首件、错订单节点、错工厂节点、空工序、负数/超量报工均被拒；合法的扎号报工只能计入所属任务及订单。

#### R5. 按实际合格产出办理部分/完整入库

- 入库以已复核的合格产出为上限，按订单明细、颜色尺码、生产任务/批次形成入库流水；不得直接以订单计划量代替实际产量。
- 支持部分完工、部分入库和多次入库；记录计划数、已报合格数、不良/报废数、已入库数、未完工数、未入库数，满足数量守恒。
- 没有有效生产报工、质量放行或可入库数量时拒绝入库；重复请求必须幂等，冲销也必须走反向流水，不得删改历史。
- 订单状态只有在所有必需任务完成且入库数量达到订单可交付量时，才进入完整「已入库」；部分状态应可识别。
- 验收：报工 60 件合格、5 件不良的批次最多入库 60 件；重复入库不能重复加库存；短数、超报、部分完工在生产看板和库存账中保持一致。

### P1：让计划、工艺和人员可执行

- 以已确认开发单/款式版本维护工艺路线，允许配置可选工序、顺序、工作中心和标准工时；不要对所有款式无条件生成同一套 13 道工序。
- 生产看板展示分单/生产任务，而不只展示订单状态；列出未开始原因（缺料、待首件、无排程、无分配等）、计划数量、累计报工、合格/不良、剩余数量和交期风险。
- 首件、裁剪扎包、报工、质检、入库使用同一订单行/颜色/尺码/批次标识，确保追溯链不依赖自由文本。
- 现货返单可复用当前有效技术版本；新款定制仍须有开发单和打版确认。两种业务路径必须有明确且可配置的技术门禁。

## 四、端到端验收场景

以下是需求验收用例，不代表本次已运行：

1. 销售创建一张多款、多色、多尺码订单；保存草稿、修改明细、提交评审后冻结版本，订单总量与明细合计一致。
2. 分别通过手工下单、已接受报价转单、客户已确认商城询价转单创建订单；三种入口最终使用同一订单明细结构，来源单号可追溯，未确认来源不能转单。
3. 不通过接单评审、技术确认、成本审批或定制打版门禁时，订单不能越级进入下一状态；每次拒绝返回缺项和责任模块。
4. 成本审批通过后分配至本厂车间；分配不足时明确剩余量，超订单量分配被拒，生产任务带有正确颜色尺码和技术版本。
5. 首件未放行时，车缝及后续工序的报工被服务端拒绝；已放行后只允许在授权数量内按正确工序/工厂报工。
6. 部分报工和部分入库不把整张订单标为完工；库存流水数量与已复核合格入库数一致。重复提交不重复增加库存。
7. 从销售订单查看，可以沿源询价/报价 → 订单版本 → 接单评审 → 成本审批 → 分单/生产任务 → 工序报工/首件 → 质检 → 库存流水追溯；从车间任务也能反查订单与客户交期。
8. 对所有状态迁移和数量调整留存操作者、时间、原因、来源单/任务、修改前后数量；回退、取消、返工、报废均能从流水中对账。

## 五、建议实施顺序

1. **继续完成 P0-R1**：本轮已禁止 `assigned` 直入库和无有效全量分单推进到 `assigned`；下一步把其它状态写入也统一委托状态机，并补充并发与重试幂等控制。
2. **完成 P0-R2、R3**：草稿结构化明细编辑和全量分单门槛已落地；下一步建立按颜色尺码的分配记录和关联到工厂的生产任务。
3. **扩展 P0-R4、R5**：报工工序归属和数量上限、整单质量放行门槛已落地；下一步补任务级报工复核、返工/报废数量守恒及部分入库。
4. **完成 P1 工艺路线和看板**，再将一个真实款式、一个本厂车间、一个外协场景做并行验收。
5. 验收覆盖订单创建、变更、取消、拆单、超量报工、短数、返工、部分入库和恢复后数据一致性，再扩大上线范围。
