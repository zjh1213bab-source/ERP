### 2.2 数据流转（关键）

```
客户登录商城
   │  POST /api/mall/auth/login （客户账号，独立 JWT scope=customer）
   ▼
浏览商品  GET /api/mall/products
   │  价格 = 客户专属价 ?? 商品公开价；可售量 = 美仓现货
   ▼
选品车（前端）→ 提交询价  POST /api/mall/inquiries
   │  生成 mall_inquiries(submitted) + mall_inquiry_items
   ▼
ERP 后台「询价处理」POST /api/mall-admin/inquiries/:id/quote
   │  逐行改价 → 合计重算 → status=quoted
   │  ↳ 自动推送客户消息「已报价」
   ▼
客户端「我的询价」POST /api/mall/inquiries/:id/confirm → status=confirmed
   ▼
ERP 后台 POST /api/mall-admin/inquiries/:id/convert
   │  生成销售订单草稿（orders + order_items + order_item_sizes，颜色/尺码=待定/均码）
   │  ↳ mall_inquiries.status=converted, order_id 回填
   │  ↳ 自动推送客户消息「询价已转订单」
   ▼
ERP 订单状态流转  POST /api/orders/:id/transition
   │  技术确认 → 财务审核 → 分单 → 生产 → 入库 → 发货 → 结案
   │  ↳ 每一步自动调用 notifyOrderStatus() 写客户站内消息
   ▼
客户「我的订单」看进度时间线 + 「消息」查通知
```

**隔离原则**：客户看不到成本、供应商、工厂、内部备注与其他客户数据；员工 ERP 接口拒绝客户 token。

**数据流转**：
```

   ↓
按标准开检验单（自动带出检验项）→ 逐项录入实测值与合格/不合格
   ↓
判定：全合格=pass / 有不良=fail / 让步=conditional
   ├─ 不合格 → 自动开异常单（返修·报废·让步）+ 批次自动「冻结」
   │             → 填根因/纠正措施 → 关闭
   └─ 合格   → 批次保持「正常」，可继续入库发货
   ↓
客诉/风险 → 发起召回评估（批次立即冻结）→ 通知客户（商城站内信）
   ↓
结案 → 批次置「已召回」；全程可在「批次追溯」一页看全链路
```

## 二·补 本版补齐：零售与渠道（TS-M04）

| 编号 | 功能 | 落地 | 实现位置 |
|---|---|---|---|
| N04-01 | 平台与主体映射 | ✅ | `channel_shops`：平台/店铺 + 经营主体、注册执照、签约主体、开票主体、收款主体、履约仓分别登记；接口授权状态独立（未授权/已授权/受限）且需人工核查确认。**店铺数与公司数无固定一一关系**，同一公司可开多店、同一店可跨主体 |
| N04-02 | 零售订单与支付核对 | ✅ | `retail_orders` + `retail_order_items`：渠道订单号唯一（按店铺去重）、实付/优惠/税费/运费/退款分行记录；**支付回执核对（含金额一致性校验）→ 预留 → 发货**三段推进；未核对支付**不释放拣配**；缺货自动标「缺货待补」不静默失败。另支持受控批量导入 |
| N04-03 | 批零库存配额与承诺 | ✅ | `channel_quotas`：按（店铺 × 款号 × 货主）设渠道限额与预留；**可分配 = min（限额 − 已预留，货主实物可用量）**，配额不是第二份实物；已预留超限额/超实物都会在页面告警；占用明细可下钻到具体渠道订单 |
| N04-04 | 渠道费率与经营损益 | ✅ | `channel_settlements`：按店铺费率生成结算批，实付/平台费/广告费/履约费/退款/其他分行；**商品毛利（只扣成本）与贡献（再扣全部渠道费用）分开呈现**；预估与账单确认两种口径，账单核对自动算差异并留痕 |

**数据流转**：
```
店铺映射（主体/收款/履约仓 + 接口授权）
   ↓
渠道订单进入（已授权走接口，未授权走受控导入）→ 状态：支付待核
   ↓
支付回执核对 ──不一致──→ 核对异常（不释放拣配，查回执）
   ↓ 一致
预留（占用渠道配额，不动实物；可分配 = min(限额剩余, 实物可用)）
   ↓
发货 → 扣美仓实物 + 写库存流水（ref_type=retail）+ 释放预留
   ├─ 实物不足 → 自动标「缺货待补」，补货后可再发
   └─ 成功 → 状态：已发货
   ↓
售后：退款（钱）与实物退回（货）两个状态独立推进，分别留痕
   ↓
结算批（只结已发货单，按费率预估）→ 账单核对（传平台实际数据）→ 差异留痕 → 确认贡献
```

**三条硬规则（已在实现中强制，不是文档口号）**：
1. 支付未核对 → 预留与发货都被拒，提示「不释放拣配」；
2. 配额不是第二份实物 → 同款两店各给 8 件限额但实物只有 10 件时，先占先得，后到的预留会被拦（实测 3 + 8 时第二单被拦，提示「限额剩余 8，实物可用 7」）；
3. 退款与实物退回互不替代 → 退款完成时退回状态仍为「待退回」，收到货才置「已收到」并可选回补库存。

## 二·补 本版补齐：客户订单与资料确认（TS-M22 N22-04 / 05 / 07）

| 编号 | 功能 | 落地 | 实现位置 |
|---|---|---|---|
| N22-04 | 样衣封样确认 | ✅ | `sample_seals`：按订单/款自动递增版本，记录**内容校验值**（款号+名称+版本+附件+备注的 SHA256 前 16 位）、附件、客户确认人/账号/时间/意见；**客户确认与总部技术批准分开记录**，缺一条不算完成。新版本创建即把旧版本置 `superseded`，旧版本的确认**不能**解除新版本阻塞。订单流向「技术确认」时强制校验最新版本双确认 |
| N22-05 | 订单与工艺变更确认 | ✅ | `order_changes`：影响评估（在制数量/材料/已交数量/剩余可变更/费用/交期）→ 总部批准 → **客户双向确认** → **生产工位签收** → 生效；未填评估不能提交客户；变更只作用于「总件数 − 已交数量」的剩余范围，不追溯已交付部分；交期类变更自动生成一条交期变动记录 |
| N22-07 | 交期变动与物流跟踪 | ✅ | `delivery_changes` 原承诺与最新预计**分行存储**（后者不覆盖前者）；`shipment_events` 区分 `manual` / `api` 来源并带核实标记。客户侧 `/api/mall/orders/:id/delivery` 同时给出「原承诺」与「最新预计」，人工记录明确标「人工登记（经业务核实）」而非实时直连 |

**数据流转**：
```
建封样版本（自动 V1/V2，算内容校验值）
   ↓ 旧版本自动置「已被替代」
总部技术批准 ──（独立于客户确认）
   ↓
发样给客户（推商城站内信，带校验值）
   ↓
┌─ 客户确认 ──→ 双向确认达成 → 订单可过「技术确认」
└─ 客户提修改 → 建新版本（校验值变，需重新确认）

订单变更：建单 → 影响评估（必填）→ 总部批准 → 推客户确认
   ├─ 客户不接受 → 驳回，业务另行沟通
   └─ 客户同意 → 待工位签收 → 工位签收 → 已生效执行（只作用剩余范围）

交期变动：登记（原承诺保留）→ 推客户确认 → 客户接受/不接受
物流事件：人工登记（待核实）→ 业务核实后置「已核实」；接口同步则标「接口同步」
```

**三条硬规则（已强制）**：
1. 客户确认 ≠ 技术批准：两者都满足才算封样完成，任何一方缺失订单都过不了「技术确认」；
2. 新版本一建，旧版本的客户确认立即失效（自动 `superseded`），实测 V1 已确认、建 V2 后门槛仍拦截并提示「V2 还未发给客户确认」；
3. 变更未经客户确认 + 工位签收不算执行；未做影响评估不允许提交客户。

**数据流转**：
```
招聘需求（需求人数 / 已到岗）
   ↓ 候选人 已投递 → 面试中 → 已发 offer（必须填薪资）→ 办理入职
生成员工档案（在职·试用期）+ 到岗数 +1 + 一条「入职」异动
   ↓ 招满 → 需求自动关闭
签订劳动合同（期限/试用期/交付证据）→ 30 天到期预警 → 续签生成新合同
   ↓
异动：转正（改任职类型）/ 调岗（改部门岗位）/ 晋升 / 离职（必须有交接清单）
   ↓ 生效日到达或被「立即生效」

   ↓
调薪：草稿 → 批准 → 生效（回写基本工资，保留前后值）→ 下次工资单按新工资算
```

**四条硬规则（已强制）**：
1. 发 offer 必须填薪资，否则不能进入 offer 阶段；
2. 固定期限合同必须有结束日期，试用期不能晚于合同结束日，同一员工两份合同时间不能重叠；
3. 异动生效日未到不改进档案；离职没填交接清单直接拒绝；
4. 调薪必须批准后才能生效，生效时才回写工资，且前后值以执行时实际工资为准。


## 二·补 本版补齐：外部接口与失败补偿（TS-M25 N25-03 / 04 / 05 / 06）

| 编号 | 功能 | 落地 | 实现位置 |
|---|---|---|---|
| N25-03 | 业务事件与失败补偿 | ✅ | `integration_events` + `POST /api/integration/ingest/:code`：外部推送必须带 **event_id 幂等键**，重复推送直接返回原结果、**不重复成单/扣货/通知**；事件先落库再处理（业务落库与消息发送分离）；失败按**指数退避**重试（2^次数分钟，上限 60 分钟），超 5 次进**死信**，可人工重放或放弃 |
| N25-04 | 物流接入与人工校正 | ✅ | 复用 `shipment_events` 并补校正字段：人工校正**必须填理由**，提交后只登记「待批准」，**由他人复核批准才生效**；批准时保留旧值（`correct_from`）、记录批准人时间，并**自动通知客户**；`source` 区分接口同步 / 人工登记，人工记录不冒充实时定位 |
| N25-05 | 接口安全和外部资料 | ✅ | `integration_endpoints` + `integration_calls`：每个接入点**独立 API Key**（新建返回一次明文，之后只显示掩码，可重置）；**按接入点限流**（超限 429）；所有调用含鉴权失败/限流都写调用日志；私有文件下载用**带过期时间的 HMAC 签名链接**，篡改或过期一律 403 |
| N25-06 | 上线运维与交付资产 | ✅ | `GET /api/integration/openapi.json` 自动生成 OpenAPI 3.0.3 清单（含鉴权参数说明），配合 `docs/DELIVERY.md` 交付清单（源码、数据库、备份恢复、监控、接口文档） |

**数据流转**：
```
外部系统（电商/物流）── POST /api/integration/ingest/<code>
   ① 校验 API Key → ② 校验限流 → ③ 校验 event_id 幂等键
        ├─ event_id 已存在 → 直接返回原结果（不重复处理）
        └─ 新事件 → 写入队列(status=pending) → 返回 202
   ↓
dispatch（手动/定时）
   ├─ 成功 → status=success，回填 result_ref（如生成的零售单号）
   ├─ 失败 → attempts+1，next_retry_at=指数退避
   └─ 达到 max_attempts → status=dead（死信）→ 人工重放 / 放弃

物流校正：人工提交（带理由）→ 待批准 → 他人复核 → 应用新值 + 保留旧值 + 通知客户
```

**四条硬规则（已强制）**：
1. 没有 `event_id` 一律拒收（400）——宁可拒，不让重试变成重复下单；
2. 同一 `event_id` 重复推送返回 `duplicate: true`，不重复落库；
3. 死信必须人工介入，可「修正数据后重放」，也可标记放弃并留原因；
4. 物流校正不许自己批自己（admin 除外），且批准后必须通知客户。
