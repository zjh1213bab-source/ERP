# 演示数据体检与清库

> 版本 v1.43.0 · 2026-10-28 · 脚本 `backend/scripts/audit-demo-data.js`

## 一、为什么要做这件事

这几轮为了验证功能，冒烟脚本往库里写了几千条带「烟测 / SMOKE」标记的数据。它们不会自己消失，
而且已经开始以三种方式伤人 —— 全部是真实数字，不是假设：

| 现象 | 数字 | 后果 |
|---|---|---|
| 研发立项里几乎全是烟测款 | 236 条里 **230 条**是 `SMOKE-744441` | 「研发立项」页打开像测试环境 |
| SKU 档案里一半是烟测 SKU | 351 条里 **230 条**是 `SMK-744441-A-3T` | SKU 选型、配码全被污染 |
| 应收台账虚增 | 43 张票，**¥210,700**，客户叫「冒烟·信用测试客户」 | 账龄、现金流预测、对账全部偏差 |
| 子表指向已删父行 | **95 行** `order_item_sizes` | 按尺码聚合的统计凭空多出 9,406 件 |

最后一项尤其值得说：这个库 **352 张表一个外键约束都没有**（全用逻辑外键）。
删掉一张订单不会报错，只会留下一堆指向空气的明细行 —— 等到某天有人对账对不上，才发现是三年前删单时漏的。

## 二、三档分类

| 档 | 判定 | 处理 |
|---|---|---|
| **L1 烟测夹具** | 标识列（单号/编码/款号/名称/用户名）**以** `SMOKE` / `smoke` / `SMK-` / `__smoke` / `烟测` / `冒烟` **开头** | 默认清理 |
| **L2 演示数据** | `demo_tag` 有值且不属于 L1 | 演示库保留；交付清库用 `--with-demo` |
| **L3 疑似** | 任意文本列**包含**「烟测 / SMOKE」，但标识列不以它开头 | **只报告，不动** |

四条判定原则，每一条都是踩过才写下的：

1. **只看标识列，不看备注**。一条真实的领料单，备注里可能写着「参考烟测数据补录」——
   按备注 `LIKE '%烟测%'` 删就会把真单据删掉。
2. **用「开头」而不是「包含」**。冒烟生成的名字天然是前缀形态（`SMOKE-744441`、`烟测员工A__SMOKE`）。
3. **`batch_no` / `week_no` / `account_no` 不是标识列**。真实领料单 `LL202610270004` 里有一个
   批次号为 `SMOKE-B1` 的明细，把它当判据会把真实单据的明细删空。
4. **显式 `demo_tag` 优先于命名推断**。演示脚本有时给款号起名叫 `SMK-xxx-SET`，
   光看名字分不清，但它自己写了 `demo_tag` —— 那就按演示数据处理。

另外两类特殊处理：

- **审计日志豁免**（`audit_logs` / `sensitive_access_logs`）：日志按设计「只增不删」，
  冒烟产生的登录记录属于正常审计痕迹，不参与清理。
- **明细表只靠级联**（表名以 `_items` / `_lines` / `_details` 结尾）：明细跟着父表走。
  父表是烟测的，明细一起删；父表是真实的，明细一条不动。

## 三、用法

```bash
cd backend

npm run audit:data                  # 体检报告（不改任何数据）
npm run audit:data -- --json        # 机器可读（给 CI / 巡检用）
npm run clean:data                  # 清 L1（自动先备份到 packages/clean-backup-*.db）
npm run clean:data -- --dry         # 预演：只报会删什么，不写库
npm run clean:data -- --with-demo   # 连演示数据一起清（交付前用）
npm run clean:data -- --include-finance   # 连财务类（应收/应付/凭证/工资）一起清
npm run verify:data                 # 清理后校验：残留归零 + 孤儿 + 关键指标
npm run audit:data -- --fix-orphans # 只修孤儿（指向不存在父行的子表行）
```

### 财务类为什么默认不删

`ar_invoices` / `ap_invoices` / `gl_vouchers` / `gl_entries` / `payrolls` 这些表删一行就改动账面数字。
正确做法是**冲销或作废**，不是 `DELETE` —— 直接删会让「总账与业务账对不上」这件事失去线索。

所以它们默认跳过，并在报告里标出金额（本次 ¥210,700），要人看过之后加 `--include-finance` 才执行。

### 删除顺序

先算「根 id 集合」，再沿引用关系把子表 id 传播进来（最多 6 层），最后按拓扑顺序
（先删没有待删子表的表）逐表 `DELETE`。没有这一步，「删 230 个研发项目」会留下
115 条挂在已删项目下的任务 —— 数据库不会拦你，只有下次有人查「任务数」时才发现。

## 五、治本：让冒烟自己证明干净

只清一次没用 —— 冒烟跑一遍又会在 `supplier_confirms` / `bank_imports` / `cost_pools` /
SKU 套装这些地方留下几十行尾巴。所以做了两件事：

1. **冒烟末尾加兜底清理**：调同一个 `clean({ includeFinance: true, skipBackup: true })`
   + `fixOrphans()`，而不是再手写一遍 `DELETE` —— **判据只有一份**，才不会「改了 A 忘了 B」。
2. **冒烟末尾加自检断言**：`★ 冒烟跑完库里没有烟测残留（L1 = 0）`。
   这条断言第一次跑就抓出 161 行残留，其中 `sku_masters` 121 行 —— 之前没人发现。

顺带修了冒烟里 3 处「删订单明细不删尺码行」的写法，这是那 95 行孤儿的生产者。

现在的状态：连续跑两次冒烟，`L1 = 0`、孤儿 0、巡检 74 页 0 异常。

## 六、后续规范

新增模块/演示数据时守三条：

1. **演示数据必须写 `demo_tag`**，并给脚本加 `--clean` 入口（按标记删，不按名字猜）。
2. **冒烟夹具自建 + 自己清**，标识带 `__SMOKE`；清理按 `name` / `remark` 删，别按 `note`
   （`review` 之类的操作会把 note 改写成成品文案）。
3. **删父行前先删子行**。这个库没有外键护航，漏一步就是孤儿；`verify:data` 会查出来。

## 七、还没做的

- **L3 的 4,400 余处**：都是真实格式单据（如 496 张领料单）的备注里写着「冒烟测试结束」。
  这些单据有真实单号与库存流水，只能走业务作废流程，不能 `DELETE`。
  建议上线前由业务口按单号清单核对一遍（`--json` 可导出）。
- **文本外键**：`order_items.sku` / `style_no` 是字符串引用，删掉档案后订单里仍显示旧编号。
  这类引用无法自动校验，只能靠页面提示「该 SKU 已不在档案中」—— 本轮未做。
