## 三、数据流向设计

### 3.1 主链路（正向）

```
客户下单 ──► 技术接收 ──► 财务核价 ──► 分单 ──► 投产 ──► 成品入库 ──► 发货 ──► 结案
   │            │            │           │        │          │          │
   │            │            │           │        │          │          └─ closed
   │            │            │           │        │          └─ shipped（扣库存）
   │            │            │           │        └─ instock（加库存 + 13 道工序报工）
   │            │            │           └─ assigned（生成生产任务）
   │            │            └─ finance（成本单 approved 才能分单）
   │            └─ tech（开发单 confirmed + 打版六阶段 done，定制单强制）
   └─ draft
```

每一步都写 `order_logs`（from_status / to_status / operator / note / 时间），详情页「流转记录」按时间线展示。

### 3.2 反审回流（逆向，已实现）

```
   draft ◄── tech ◄── finance ◄── assigned ◄── production ◄── instock
     ▲        ▲         ▲           ▲             ▲            │
     └────────┴─────────┴───────────┴─────────────┴────────────┘
                    POST /api/orders/:id/rollback { to, reason }
```

规则：

| 规则 | 说明 |
|---|---|
| 只能往前退 | 目标状态必须在当前状态之前，不能越过 draft |
| 已发货/已结案不可退 | 走退货流程（`channel.js` 的 receive-return / confirm-refund） |
| 原因必填 | 写进 `order_logs.note`，格式 `[反审退回] 原因` |
| 库存自动冲销 | 从 instock 退回时，按 `stock_ledger` 净额反向扣减；货已出库则拒绝并提示 |
| 工序自动重置 | 从 production 之前退回时，13 道工序回到 pending，备注追加 `[反审退回作废]` |
| 事务保护 | 全程 `BEGIN/COMMIT/ROLLBACK`，库存不足时整单回滚，不留半截数据 |

### 3.3 其他已实现的跨模块流转

| 触发点 | 去向 |
|---|---|
| 订单状态变化 | 客户商城站内消息（`notifyOrderStatus`） |
| 订单 → 生产 | 自动生成 13 道工序（`ensureNodes`） |
| 订单 → 库存 | `POST /api/stock/instock` 按明细加库存，`/ship` 扣减 |
| 打版完成 | 归档样衣快照（`sampleArchives`），开发单锁定 |
| 样衣变更审核通过 | 开发单回 draft、打版流程回 pattern 阶段 |
| 客户订单确认 | 商城侧封样/变更确认 → ERP 侧状态联动（`confirm.js`） |
| 渠道发货失败 | 失败补偿 + 人工校正（`integration.js`） |
| 首件放行 | 车缝工序节点写备注 + 报工门禁由「拦截」变「放行」（`faGate`） |
| 首件退回 | 退回销售 / 总部技术，退因写入工序备注；工厂不自行改版 |
| 技术版改版 | 旧首件自动失效（`stale`），报工重新拦截，需按新版重做 |
| 采购到货 | 生成收料单（待检），**不再直接加库存**；检验合格才进 `materials.stock_qty` → 齐套与裁床才认 |
| 来料退回 | `purchase_items.received_qty` 回退，采购单回 `ordered` 等供应商补发 |
| 邮件关联源单 | 只读投影当前状态 + 权限受控链接；邮件里改不了原单，回复「好了」不等于业务完成 |
| 需确认 / 需办理 | 逐人确认回执写入 `mail_recipients`；无原任务时建唯一协同任务（一交付物一主责） |
| 客户身份 | 服务端每次按账号现读 `customer_id` 与权限点；停用/改权限立即生效 |
| 客户权限上限 | 销售批上限 → 主账号在限内分配子账号 → 收紧时联动裁剪已开子账号 |
| 客户金额字段 | 无 `finance.view` 时服务端不出金额字段，不是前端隐藏 |
| 供应商评价 | 样本只来自收料单（承诺日 vs 到货日、合格/冻结/退回），所有供应商同一套公式 |
| 备用产能 | 技术+封样+合规三项全过才可用；选源按综合分排序，**不按最低价** |
| 供货资格 | 评价 → 整改/备用验证 → 资格；`suspended` 的供应商在采购下单时被 400 拦住 |\n| 客户停单改量 | 减量只动「未交」且要供方确认；已收未用的走退料，齐套在途自动跟着变 |\n| 退料结算 | 实物回执扣库存 + 记已退；贷项凭证冲应付，不直接删财务行 |
| 返工报废 | 复验通过才闭环 → 损失自动写 cost_entries 的 rework 层 → 毛利被扣减（同单只写一次） |
| 生产结单 | 五项检查；硬阻塞不许结，软提示只能部分关闭 + 争议挂账（争议说明/余额来源必填） |
| 设备停机 | 登记即把设备从可承诺产能扣除；安全复核必须人工确认（登记人不能自放，admin 除外） |
| 产能日历 | 按工作中心算 基准台时 / 停机占用 / 可用台时 / 产能损失，并列出受影响订单 |
| 绩效建议分 | 只从报工/考勤/返工三类实测数据生成；订单超期标「待配置」不预测、不扣分；批准休假覆盖的迟到不计 |
| 绩效确认分 | 建议分不生效，主管逐项复核后才计入当前分；驳回必须写原因 |
| 绩效申诉 | 申诉后分数转「暂定」（final_score=null），独立复核人调整后重算；冻结周期也能申诉但保留原记录 |
| 合同履约提醒 | 到期/付款/验收/押金返还只生成任务进日历；**不自动改合同状态、不自动扣款、不自动续约** |
| 续签与终止 | 续签必须写依据并顺延到期日；终止必须写原因，付款/验收/续约任务转豁免，押金返还仍保留 |
| 用印门禁 | 印章按公司独立授权（人/角色/岗位 + 范围 + 有效期）；申请绑定合同当前版本内容指纹，改正文自动转「需重核」 |
| 借章与归档 | 借章必须写预计归还日，逾期进日历；归还留回执；合同归档保留不删除 |
| 审批超时 | 按步 SLA 算截止；同任务同级别只提醒一次；超时只升级到人，**不自动 approve** |
| 审批失主 | 主责按「原审批人 → 有效代理 → 升级接收」流转，无代理即进升级队列，历史保留 |
| 制度生效 | 只有 effective 版本是当前做法；四要素齐全才能发布；旧版转 retired 可查不执行 |
