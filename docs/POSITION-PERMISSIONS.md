# 权限管理

入口：分析与系统 → 权限管理（系统管理员）。旧 /access-review 和 /position-permissions 链接均跳转 /permission-management，不再提供独立复核授权界面。

左侧新增、编辑或删除岗位，右侧直接选择各模块的查看权限以及新增、编辑、删除、停用、启用等按钮，再分配账号。选择动作会自动补齐对应模块访问与既有业务页面所需的兼容标识；不必再选择业务职责、操作入口、旧写权限或复核签字。配置保存即时生效，不需要重新签发登录令牌。侧栏只显示岗位授权的模块，顶部显示岗位名称。

岗位授权为分配账号的唯一权限来源，不再被历史用户级复核 allow/deny 或旧主岗覆盖。已有岗位在读取时兼容同一模型，不重写历史配置。未分配新岗位的账号保留既有默认权限；移出岗位仍只保留本人自助。管理员账号不能分配普通岗位，有成员的岗位不能删除。

删除、停用、启用独立控制。客户、供应商、物料、产品、工厂、工序类别 DELETE 实为停用；报价草稿删除和子资源删除仍为真正删除。编辑档案时，后端比对当前状态，真实状态改变另需启停权限。前端 v-action 控制按钮显示，直接请求接口同样校验。字段明文权限可在对应模块独立勾选。系统管理员专属接口、主体范围、审批人与处理人分离及业务状态校验继续执行。

数据继续使用 app_config 的 access_positions_v1 键，无表结构变化。revision + BEGIN IMMEDIATE 防止并发覆盖；保留修改前后快照、操作人、时间与版本。在同页“变更记录”查看最近变更。历史复核记录继续留存在数据库，不再参与新岗位授权覆盖。所有生效权限仅由 GET /api/access/me 下发。

基础账号可用本人自助、本人异常、扫码基础查询、助手工作指引、内部邮件；仍不能查看其他员工异常或经营工资数据。获得自定义岗位后按模块和按钮授权访问。

验证：test-position-access.js 17项、test-position-http.js 69项、test-position-ui.js 19项；前端构建、相关页面深浅色巡检、RBAC、数据体检和结构一致性检查。全量冒烟仍因 smoke-test.js:1286 空库采购夹具缺失退出，不计为全量通过。

部署：frontend 下 npm run build，随后 deploy/win/reload-lan-preview.ps1，核对 /api/health 的 code_stamp 与磁盘一致。无新增密钥或配置参数。回滚前保存权限配置备份，不要简单删除配置键导致恢复旧角色授权。
